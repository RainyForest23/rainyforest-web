An energy cost model for AI workloads on shared servers

A model that splits a shared server's measured energy between the workloads running on it. Checked against each workload measured alone, the split was within about 5 %. Published in Mathematics (MDPI, SCIE), 2026. [Draft]

01

Decision [Draft]

Whose decision does this help?

An operator runs many tenants' workloads on shared servers and has to decide what each one pays.

Today the bill follows what was handed out: cores, memory, the type of GPU. This work supports a different decision: how much of a server's energy to charge to each workload when several run on it at once.

The question matters now because energy has become a large part of what AI workloads cost to run.

02

Before [Draft]

How was it done before, in numbers?

Billing by allocation. Two workloads given the same 2 cores, 4 GB and 1 GPU pay the same.

  • Measured alone on that same slice, a ResNet workload drew 145 W above idle and a Node.js web server 14 W.
  • Across the AI workloads tested, that is 4.8 to 10.5 times the web server.
  • Run together in pairs, the gap was 4.7 to 11.0 times.

Measuring each workload directly is not an option. Once two workloads share a machine, the meter at the wall gives one number for both.

Earlier energy models mostly predict CPU power from how busy the CPU is. That leaves out the GPU, where AI workloads spend most of their energy, and it mishandles parts such as memory that draw power whether or not they are being used.

03

Ontology [Draft]

What are the objects, how are they related, what can be done to them?

Server
One physical machine. Its total energy is read at the wall.
Part
CPU, GPU, memory, storage, and everything else (power supply loss, fans, the board). Each part has an idle energy and a measured energy.
Workload
One tenant's program, running in its own slice of the server.
Allocation
What a workload was given: cores, an amount of memory, a share of the GPU.
Usage
What a workload did: how busy it kept the CPU and the GPU, how many bytes it read and wrote.
Interval
The window of time over which energy is counted.
Measurement
A reading of one part over one interval: the wall meter, the CPU's own energy counter (RAPL), the GPU's power interface (NVML), per-slice statistics (cgroup).

Actions: measure a part, split a part's energy across workloads by that part's rule, sum the parts for each workload, and check that the workloads plus the machine's own baseline add up to the wall reading.

04

Smallest version [Draft]

What was the smallest version that worked, and what were the sub-problems?

One idle server and one workload. Measure the server idle, run the workload alone, subtract.

That gives each workload's own energy. Later it is the reference the split is checked against.

  • Split a shared server's energy between workloads
    • Measure the whole machine
      • A current clamp on the power cable, logged every second
    • Measure each part
      • CPU from its energy counter
      • GPU from its power interface
    • Tell workloads apart
      • One slice each: 2 cores, 4 GB, 1 GPU
    • Split each part by its own rule
      • CPU, GPU, memory, storage
    • Check the split
      • Workloads + baseline = wall reading
      • Share under sharing vs the workload alone

Then the full run: idle, each workload alone, and six pairs (three AI workloads each with the web server, and the three AI pairs). Every experiment was repeated five times and averaged.

05

Trade-offs [Draft]

What were the options, and why this one?

CPU: by use
Power is not strictly proportional to use when the chip changes frequency. Tracking frequency per workload would add monitoring cost, and frequency follows the total load rather than any one workload. So the measured CPU energy, minus idle, is split by how busy each workload kept it.
GPU: reserved, plus used
A GPU draws power for being held, even with little to compute. Charging only by use would make that part nobody's. So the idle part follows the reservation and the rest follows use.
Memory: by amount held
Memory power is mostly static. Charging by access would undercharge a workload that holds memory without touching it. So memory is charged by the amount held, at 0.2 W per GB.
One GPU per workload
Each workload ran on its own GPU rather than a partitioned one. That gave clean GPU readings per workload without needing partitioning support. The cost: a GPU shared between workloads was not tested.
No extra instruments in the model
The split uses only counters and statistics a server already exposes. It is coarser than instrumenting every component, and it can be deployed as it is.
06

What broke [Draft]

What failed, and how was it fixed?

The wall reading looked flat
In several runs the wall power stayed at the idle level whatever was running. The server's clock and the logger's clock had drifted apart, so the two logs were being lined up at the wrong moments. Fixed by keeping both in time sync.
The logger went quiet
During the AI + AI pairs the wall logger stopped responding, so those wall readings are missing. They were approximated from the neighbouring intervals.
Two sets of numbers
The paper reports runs at a fixed CPU frequency. The raw logs, averaged over six runs, give different absolute values: the web server's whole-system power is 64 W in the paper and 77.9 W in the raw average. Each number now says which condition it comes from.

Measured [Draft]

What was the result, and how do we know?

The check: take each workload's share when two run together, and compare it with the same workload measured alone.

PairError of the split
AI + web server0.1–0.4 % for the AI workload, 0.4–4.1 % for the web server
AI + AI, unequal energy2.4–5.2 %, average 3.7 %
AI + AI, similar energy1.8–2.0 %

The largest error was about 5 %. The web server's percentage looks larger than the AI workloads' because its energy is small, not because the miss in watts is bigger.

With the same allocation, energy differed by 4.7 to 11.0 times in the AI + web server pairs, and by 2.2 and 2.4 times in two of the AI pairs.

Next [Draft]

What is the next version?

  • From slices to virtual machines, which is how tenants are actually separated.
  • A billing model on top of the split.
  • A GPU shared between workloads, which this experiment avoided.

None of these is done yet.
